### 1. TanStack StartがReact Server Componentsの革新的サポートを発表（Next.jsとの比較）

| 項目 | 詳細 |
|------|------|
| 投稿者 | いまいまい (@imaimai17468) |
| 投稿日時 | 2026年4月14日 09:26（日本時間） |
| エンゲージメント | ❤️ 202 / 🔁 31 / 💬 1 |
| リンク | [元ポスト](https://x.com/imaimai17468/status/2043848366808018946) |

**投稿内容:**

> TanStackが2026年4月13日に、自社フレームワークTanStack StartにおけるReact Server Components（RSC）のサポートを発表しました。
> 
> 従来のNext.jsなどはサーバーがコンポーネントツリー全体を管理し、クライアント側は「use client」ディレクティブでインタラクティブ部分をオプトインする設計です。一方、TanStack StartではRSCをサーバー関数から返されるFlightストリームとして扱い、クライアントが自らのタイミングでフェッチ・キャッシュ・レンダリングを行うアプローチを採用しています。
> 
> TanStack QueryやTanStack Routerの既存キャッシュ機構をそのまま活用可能で、「use server」アクションは使わず、明示的なRPCのみをcreateServerFnでサポートします。また「Composite Components」という新機能も導入。サーバー側でレンダリングしたUIの中に、クライアントが後から埋め込むスロットを設ける仕組みで、「use client」ディレクティブなしに通常のReactのchildrenやrender propsで実現できます。
> 
> 自社ブログとドキュメントページへの適用結果として、クライアントJSバンドルサイズを約153KB削減。Lighthouseスコアは52から74に向上、Total Blocking Timeは1200msから260msに短縮されました。ただし、ダッシュボードのようなインタラクティブUI中心のページでは効果が小さく、主にコンテンツ重視で依存ライブラリが重いページに適しています。現在は実験的機能として提供されています。

**解説:**

この投稿は、Next.jsが長年推進してきたReact Server Components（RSC）のアーキテクチャに対し、TanStack Startが全く異なる「クライアント主導」のアプローチを取った点を詳細に分析した技術解説です。Next.jsではサーバーがRSCツリーを所有するためキャッシュ戦略が複雑になりやすい一方、TanStackの方法は既存のTanStack Queryキャッシュを活かしやすく、クライアント側で柔軟に制御できるのが強みです。実際の適用事例としてパフォーマンス改善数値を具体的に示しており、RSCの実践的なユースケースと業界動向を理解するのに非常に有益な内容です。Next.jsユーザーにとって、今後のフレームワーク選択やアーキテクチャ検討の参考になる分析と言えます。

**投稿内容:**

> VercelもオープンソースのAgentホスティングプラットフォーム「open-agents」を公開しました。
> 
> 試用したところ成熟度が高く、企業内へのカスタマイズ（二開発）がしやすい設計です。予想通り、Vercelは「Agent not in sandbox（Agentはサンドボックス内にいない）」という設計を採用しています。
> 
> 詳細はGitHubリポジトリ（https://github.com/vercel-labs/open-agents）で確認できます。

**解説:**

Vercelが自社で開発・利用しているAIコーディングAgentのホスティング基盤をオープンソース化したことを紹介した投稿です。従来のAgentフレームワークではAgent本体とコード実行環境（サンドボックス）を同じコンテナ内に閉じ込めることが多かったのに対し、「Agentをサンドボックス外に置き、ツール呼び出しで外部から操作する」という分離アーキテクチャを採用している点が特徴です。これによりAgentのライフサイクル、実行環境、利用モデルの独立した進化が可能になり、大規模コードベースや企業内知識に対応しやすくなります。StripeやSpotifyなどが自社AIソフトウェア工場を構築している背景にも触れられており、Next.js/VercelエコシステムにおけるAI×開発ワークフローの最新動向を具体的に示す実践的な情報です。
